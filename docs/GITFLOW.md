# Git Flow и процесс разработки ChillTransfer

## Ветки
| Ветка | Назначение | Правила |
|---|---|---|
| `main` | Стабильная ветка, релизы | Только проверенные (reviewed) слияния; теги `vX.Y.Z` ставятся отсюда. Прямые пуши запрещены. |
| `develop` | Интеграция активной работы | Все feature-ветки сливаются сюда. Прямые пуши запрещены. |
| `feature/<task>-<slug>` | Одна задача = одна ветка | Создаётся из актуального `develop`. Пример: `feature/thermal-governor`. |
| `release/X.Y.Z` | Подготовка релиза | Из `develop`; только фиксы, без новых фич. |
| `hotfix/<issue>` | Срочные исправления | Из `main` → слияние в `main` + backport в `develop`. |

## Этапы цикла (поэтапно)
1. **Планирование** — задача фиксируется в `docs/TASKS.md` (описание, критерии приёмки, целевая ветка). Без записи задачи feature-ветка не создаётся.
2. **Реализация** — работа на `feature/*`; conventional commits: `feat|fix|test|docs|refactor|chore(scope): сообщение`.
3. **Тестирование** — до открытия MR: локально зелёные unit-тесты + сборка под целевые платформы (CI: build matrix Windows/Linux/macOS).
4. **Слияние и ревью** — MR `feature → develop` с минимумом одного ревью; после слияния в `main` выполняется **post-merge review** по чеклисту: соответствие спецификации, покрытие тестами, отсутствие регрессий, корректность CI. Только после успешного post-merge review ставится тег/релиз.

## Правила для агентов-исполнителей
- Одна задача = одна ветка из актуального `develop`; параллельные агенты работают в отдельных worktree (один writer на каталог).
- Прямые пуши в `main` и `develop` запрещены — только через слияние.
- Перед слиянием: тесты зелёные, сборка целевой платформы успешна.
- После слияния в `main`: отдельный этап post-merge review (отдельный агент или владелец) до постановки тега.

## CI (GitHub Actions)
- На каждый MR: `cargo test` + build matrix (ubuntu-latest / macos-latest / windows-latest).
- На тег `v*`: сборка артефактов для 3 платформ.
